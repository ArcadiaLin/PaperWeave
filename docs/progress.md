### 算子设计

以下为面向知识积累与复用的候选算子，供后续收敛接口与研究范围；不表示全部都要实现，也不预先将每个算子视为论文贡献。

| 候选算子 | 输入 | 输出与职责 | 当前状态 |
| --- | --- | --- | --- |
| `find_entities`：实体候选检索 | 称呼、描述、实体类型 | 返回按名称、别名与描述召回的候选及召回依据，供后续身份判断 | 已有 notebook 原型 |
| `find_statements`：命题与问题候选检索 | 陈述或问题、范围描述、类型 | 返回 Claim、ClaimConcept、Issue 候选；具体 Claim 可供检索和引用，各论文的来源记录仍分别保存 | 已有 notebook 原型 |
| `expand_context`：关系展开 | 起点记录、关系路径、筛选条件 | 返回相关记录与连接关系，如方法对应的主张、实验、资源使用经验 | 待设计 |
| `trace_evidence`：依据追溯 | 节点或关系 | 返回来源、原文位置、实验依据与核验记录，区分作者报告、Agent 判断和实际观察；取得依据不等于已验证内容 | 待设计 |
| `compare_records`：条件化比较 | 多条记录、比较问题或维度 | 返回有依据的异同与条件对照，保留缺失信息和未知项，辅助判断可比性与适用范围 | 待设计 |
| `resolve_entity`：身份判断 | 新对象描述、已有候选 | 返回复用已有身份、新建或暂不能确定的建议及理由；不直接执行写入 | 待设计 |
| `relate_statements`：命题关系判断 | 新主张、相关主张或问题 | 返回共同命题、共同问题、支持、限定或质疑等关系建议及依据；保留条件差异与各 Claim 的来源 | 待设计 |
| `assemble_context`：面向意图的上下文组装 | 研究意图、候选知识、上下文预算 | 组合关系展开、比较与依据访问，选择相关知识并保留影响判断的条件和依据，说明缺失或未展开的内容 | 候选复合算子 |
| `apply_delta`：增量写入 | 新建、关联、修改等变更及其依据 | 检查结构与引用约束，执行写入并记录变更；结构检查不替代语义正确性核查 | 待设计 |

候选召回、语义判断与实际写入分别检查，以区分召回遗漏、对齐错误和写入错误。当前较值得深入研究的方向是跨论文语义对齐，以及保留条件和证据的上下文组装；误归并修正、关系撤回与修订影响传播是否纳入核心范围仍待讨论。下一步用具体研究意图明确各算子的返回结构、语义边界和失败情况。

“A、B 都在同一个 benchmark 上报告收益，它们能否直接比较？”

find_entities 定位方法与 benchmark。
expand_context 找到具体实验、资源使用记录、指标和相关 Claim。
compare_records 对齐切分、训练量、候选集合、后处理等条件。
trace_evidence 对关键差异回查设置与结果依据。
assemble_context 返回供 Agent 判断的比较材料，保留差异和未知项。
如果形成了值得长期保存的新联系，经关系判断后由 apply_delta 写入。

### 主张分层：两条主张由不同实验支撑（2026-10-01）

核心贡献仍是**学术理解经验的复用**：一次阅读形成的理解，在后续研究任务中带着条件、来源与版本被继续使用。本研究不与通用知识图谱竞争。“公平配置会收窄主张”只针对访问层这一子主张，不收窄核心贡献。

| | 主张 A：理解经验复用（核心贡献） | 主张 B：访问层（收窄后的子主张） |
| --- | --- | --- |
| 回答的问题 | 把论文理解积累为带领域语义的持久知识，能否让研究任务做得更好或更省 | 在同一份已存知识上，任务级算子是否比 schema 说明 + Cypher 更易正确使用、更少丢失语义 |
| 对照对象 | 不复用：Agent 每次重读论文，或论文切块 RAG / grep / 全文检索 | 直接 Cypher、查询模板；基线获得相同配置、词表、规则、绑定与读取策略 |
| 主要度量 | 任务质量、证据支持、总成本（计入构建成本及其在多次任务上的摊销） | 绑定丢失率、错误率、修正次数、重新规划次数，而不只是调用次数 |
| 与通用 KG 的关系 | 不竞争；展示通用表示会丢掉的领域语义 | 不竞争；对照中的基线本就使用我们的领域模型 |

- **主张 B 的对照不检验领域模型的价值**，因为基线用的就是同一份领域知识；领域模型的价值由主张 A 的对照证明。
- 主张 B 收窄后，算子相对“Cypher + 程序编排”的剩余价值是：契约稳定、易于正确调用；组合时保留绑定、覆盖和来源；规则与词表的跨任务复用摊薄构建成本。
- 应对“为什么不用通用 KG / GraphRAG 做记忆”：不去比赛，而是在真实实例上展示通用表示丢失领域语义后的具体错误——实验条件被静默合并（同数据集不等于同切分与协议）、声明与核验强度混淆（声称开源 / 找到仓库 / 跑通 / 复现，且绑定资源版本与时间）、共同命题与共同问题混用、已存判断被当作本次验证。I3/I6 审计已列出这些错误形态。
- 第一个真实 I3 实例应同时记录两类数据：B 侧的绑定、规范化状态与判断点数量；A 侧的“不复用、每次重读”所需材料量、模型调用量及出错位置。

| 指称解析 | 这个“DPR”是哪个对象 | 带作用域的 alias 加写入时唯一约束，用规则判定 | 第三级候选，以及首次出现的新说法 |
| 取值规范化 | `dev-small` 是哪个切分，`nDCG@10` 指什么 | 作用域内注册映射，本质上就是 alias | 词表外的新写法 |
| 需求解释 | 把自由文本需求拆成条件 | 任务模板（I3.1、I6.1） | 模板以外的需求 |
| 开放判断 | 可比性、证据支持、适用性 | 复用已存的、带条件的判断，加上规则 | 本次确实需要的新判断 |

前三类可通过构建正确性或任务模板压缩运行时调用；开放判断是保留语义计算的主体。

#### 待决问题

- **alias 冲突策略：** 写入时遇到作用域唯一键冲突，应默认拒绝注册并返回冲突对象，由外部决定合并、改作用域或放弃；只有批量导入或事后核查发现的既有冲突才把键降级为 `ambiguous`。当前文档写的是直接降级，待修正。
- **规范化函数：** “规范化后的 name/alias”所用规则（大小写、连字符、空白、Unicode 等）尚未定义，它直接决定唯一键是否冲突，需要声明并版本化。
- **`Resolve` 签名：** type 与 kind 混用（切分属 Entity，协议、指标属 Concept）；三级都无命中时缺少 `none` 状态；I6.2 中“已有资源说法”的来源若需从描述中抽取，应显式记为 `A_map`。
- **§6.1 `matched` 分支：** 丢失了命中的被测对象及 `EVALUATES.role`（target / baseline），与“返回实际命中对象”的契约不一致。
- **版本未知时的切分作用域：** 论文常写“MS MARCO dev”而不注明版本，此时作用域取数据集身份并返回 `ambiguous`，还是按领域配置取默认版本，待实例测量。
- **三分类的两条轴：** Proposition、Issue 因跨来源共享被归入 Concept，但其检索方式更接近 Content，字段与 Concept 契约不匹配。
- **v1 关系回补：** `HAS_METHOD.role`、`EVALUATES.role`、`ON_TASK` 等尚未回到 v2 关系表。
