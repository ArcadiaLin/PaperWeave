# 项目视图：Fork、Merge 与项目卡

> **记录日期：** 2026-10-08。**状态：** 设计，未实现。第 2 节的五项决定已与用户商定（2026-10-08）；其余是候选设计，进入实现前逐项讨论。
>
> 机制背景见 [版本化知识管理备忘](../../discussions/2026-10-05-versioned-knowledge-management.md)（下称"备忘"）§5–§8：Fork 是选取而不是克隆，三种"不在"，上下文闭合，单父重放与改前值核对，以及不变式。历史读取见 [读取接口](./versioning_interfaces.md)。备忘中的 `Sync` 与 `Promote` 在本文合称 Merge，按方向区分。

## 1. 定位

**项目视图**是一条研究线路的知识状态：

- 从全局库的一个固定提交出发，选取成员，补齐必要上下文；
- 之后在项目内独立使用和积累；
- 显式地吸收全局的更新，或把成果回流到全局。

它对应叙事草稿的 C3（选取与必要上下文）与 C4（独立演化与历史）。

Fork 与 Merge 是**任务**，不是算子，也不是自动执行的 pipeline 或 workflow：

- **Agent 按 skill 描述的工作模式决策。** 用哪些对象、补不补某个上下文、冲突怎样决议，都由 Agent 判断，并在交给中间件的请求中写明理由。
- **中间件提供检查与执行。** 闭合检查、改前值核对、查重、物化与提交记录由中间件完成。它们和 Commit 一样，采用先预演（dry_run）后执行（apply）的工具形式。

这与"语义判断外置、契约内化"的分工一致：skill 规定的是做事的顺序与要交代的内容，不替 Agent 做判断；中间件保证的是相对于显式契约的性质，不判断选择是否充分。

## 2. 已定的决定

| # | 问题 | 决定 |
| --- | --- | --- |
| 1 | 项目库的物理形式 | **每个项目一个 Neo4j 实例。** 算子代码不变，项目目录的 MCP 登记指向它。这是工程落地的选择；评测时借助镜像部署 |
| 2 | 跨库的 id | **所有库统一向全局库申请 id。** 同一对象在各库中 id 相同，Merge 不做 id 映射 |
| 3 | 必要上下文 | **复制进项目库。** 在 `origin` 中把它标为"上下文"而不是"成员"；节点本身不加标记，不改模型 |
| 4 | AGENTS.md | **进入版本历史，作为 Artifact 管理和寻址。** Artifact 的文档是文件系统中的 Markdown 文件，通用 Agent 可以直接用自己的工具阅读 |
| 5 | 谁来推进 Fork、Merge | **Agent 按 skill 描述的模式决策**，不做成自动化的 pipeline |

## 3. 项目的组成

一个项目由四样东西组成：

- 工作目录：通用 Agent 在其中启动；
- 项目库：一个 Neo4j 实例；
- 项目卡：工作目录中的 `AGENTS.md`；
- skill：Fork 与 Merge 的工作模式。

```text
~/research/                           研究工作区（在仓库之外）
├── AGENTS.md                         全局库的卡片：库里有什么，对应哪个提交
├── .agents/skills/
│   ├── paperweave-fork/SKILL.md      Fork 的工作模式
│   └── paperweave-merge/SKILL.md     Merge 的工作模式
├── .pi/mcp.json                      PaperWeave → 全局库
├── ett-comparison/                   项目（Fork 产生）
│   ├── AGENTS.md                     项目卡
│   ├── .pi/mcp.json                  PaperWeave → 项目库（另带全局库的连接，见 §7.3）
│   └── patch-variant/                项目内的试探线（对项目再 Fork 一次）
│       ├── AGENTS.md
│       └── .pi/mcp.json
```

**目录层次就是范围层次。** pi 从工作目录逐级向上加载 `AGENTS.md`，并从工作目录及其上层发现 `.agents/skills/`。Claude Code、Codex 等支持 Agent Skills 与 AGENTS.md 的 Agent 也一样。所以：

- 在试探线目录中启动的 Agent，能依次看到全局、项目、试探线三张卡；
- skill 放在工作区根目录一次，所有项目都能发现；
- 不需要改 Agent 的配置。

**与"只控制工作目录"的关系。** 项目卡与 skill 都是工作目录中的文件，由中间件生成或随中间件提供，是被评测系统的一部分，不是替换系统提示。分工保持不变：

- 单个工具怎样用，只写在 MCP 工具说明里；
- 跨多个工具、需要判断的工作模式写在 skill 里；
- 项目本身的内容写在项目卡里。

三者不互相重复。

**物理形式。** 每个项目库是一个独立的 Neo4j 社区版实例：

- 小堆配置（候选：堆 256 MB，页缓存 64 MB），按项目分配端口；
- 容器由人启动，Fork 只往一个已登记且为空的实例里写；
- 每个实例有自己的 graph-vc 历史，`main` 是该实例的唯一分支。

全局与项目之间、项目与试探线之间的关系，由根提交上的 `origin` 与合并提交上的 `merged_from` 记录（§5.3、§6）。graph-vc 现有的 `Branch` 节点仍只用 `main`；同一实例内的多分支不在本设计中使用。

**材料与 Artifact 文档共用文件。** 材料与 Artifact 文档按路径与内容哈希登记，写入后不可变，所以项目库直接登记同一个文件，不复制文件本身。

## 4. 项目卡（AGENTS.md）

### 4.1 两种身份：工作副本与已记录的版本

工作目录中的 `AGENTS.md` 是**工作副本**，Agent 与人都可以随时修改，这是这类 Agent 记项目记忆的常见做法，不阻止。

**已记录的版本**是项目库中的一个 Artifact：

- `op` 为 `ProjectCard`；
- 文档是当时 `AGENTS.md` 的完整内容，按内容哈希存为不可变文件；
- `USED` 指向卡中列出的成员与上下文，以及上一版项目卡。

二者的关系类似 git 的工作区与已提交版本：

- **记录：** 把工作副本存为一个新的项目卡 Artifact，产生一个提交。
- **渲染：** 由项目库的状态重新生成工作副本中的生成区（§4.2），笔记区原样保留。
- **检查：** 工作副本的哈希与最近一版项目卡不同，说明有尚未记录的修改；项目卡对应的提交早于项目库的头提交，说明卡已落后。两者都可以在读取时报告，不自动处理。

旧版项目卡与其他 Artifact 一样，可以用 `AsOf`、`ReadEvidence` 读取。回看某个旧状态时，当时项目卡里写了什么也能读到。

### 4.2 内容

项目卡分两区，用 HTML 注释标出边界：

| 区 | 谁写 | 内容 |
| --- | --- | --- |
| 生成区 | 中间件渲染，每次渲染整块覆盖 | 项目问题与范围；来源（全局库的哪个提交）；成员与上下文的 id 和一句话说明，附选入理由；外部引用；项目库的头提交与本卡对应的提交；最近的合并 |
| 笔记区 | Agent 或人 | 自由书写：阶段性结论、待决事项、约定、下一步 |

规则：

- **短，只作索引。** 卡每轮都进入 Agent 的上下文，所以只给 id 与一句话说明，详细内容由 Agent 按 id 去读。生成区要有大小上限，超出时按类别给数量与代表项，完整清单用 Search 或 Traverse 查。
- **不写工具用法。** 工具说明与 skill 已经覆盖；卡里写用法会使"工具说明是否清楚"无法单独观察。
- **id 是 Agent 的入口。** Agent 可以直接用自己的文件工具读 Artifact 文档，也可以用 ReadEvidence 按行读。前者更自然，后者带哈希核对与行号，二者都允许。评测时，直接读取 Artifact 文档不算绕过中间件；直接读取论文原文仍要记录（AGENTS.md）。

### 4.3 全局卡

工作区根目录的 `AGENTS.md` 是全局库的卡，形式相同，生成区给出：

- 全局库的规模（论文数、各类对象数）；
- 头提交；
- 已有项目及其来源提交。

全局卡是否也进入全局库的版本历史，待定（§10）。

## 5. Fork：建立项目

### 5.1 工作模式（skill 的内容）

| 步 | Agent 做什么 | 用到的工具 | 要交代的内容 |
| --- | --- | --- | --- |
| 1 | 写下项目问题与范围 | — | 写进请求的 `question` 与 `scope` |
| 2 | 固定来源状态 | `Log` | 选定全局库的一个提交，之后都在它上面读 |
| 3 | 召回候选 | `Search`、`Resolve`、`Traverse`、`AsOf` | — |
| 4 | 选定成员 | — | 每个成员附一句理由 |
| 5 | 预演 | `Fork`（dry_run） | — |
| 6 | 处理计划中的待决项 | 同第 3 步 | 补上下文、改为外部引用，或不选入，并写明理由 |
| 7 | 执行 | `Fork`（apply） | — |
| 8 | 在新目录中续写笔记区 | 文件工具 | — |

skill 写清楚步骤、每步要交代什么、什么时候停下来问用户（例如计划规模远超预期，或要求结论不依赖某篇论文）。它不规定选什么。

### 5.2 中间件：闭合检查（dry_run）

输入：

- 来源提交；
- 成员 id 及理由；
- 声明为上下文的 id 及理由；
- 外部引用；
- `question` 与 `scope`。

中间件按闭合契约计算：成员要在项目中可解析，还需要什么。候选规则：

| 成员 | 需要的上下文 |
| --- | --- |
| Experiment | 所属论文、它评测的方法、用到的数据集与基准（边上带的条件随边复制） |
| Claim、Contribution | 来源论文、所关于的对象 |
| Observation | `ABOUT` 与 `FROM` 指向的对象；指向 Artifact 时按下一行处理 |
| Artifact | `USED` 指向的全部对象与 Artifact，递归；或改为外部引用，或不选入该 Artifact（备忘 §5.3） |
| 任何对象 | 材料（`MATERIAL_OF`）与名称（NameKey）随对象一起带上，不单列 |

输出计划：

- 成员；
- 自动补入的上下文，每项附"因谁而需要"；
- 外部引用；
- 待决项：Artifact 输入是否展开，规模超限等；
- 预计规模：节点数、关系数、材料数。

计划只描述，不写入。规则只沿已存的关系走，不判断语义上是否需要；"留下的理解从未用过 A"这类判断不由闭合检查保证。

### 5.3 中间件：物化（apply）

1. 核对目标实例已登记、为空，且与 dry_run 时的来源提交一致。
2. 从来源提交的状态（`state_at`）中取出成员与上下文的子图，写成项目库的**根提交**。根提交没有父提交，记 `origin`：

   ```yaml
   origin:
     store: global          # 来源实例的登记名
     commit: commit_000032  # 来源提交
     question: …
     scope: …
     members:  [{id, reason}]
     context:  [{id, reason, needed_by: [id]}]
     external: [{ref: global@commit_000032::art_0023, reason}]
     excluded: [{id, reason}]   # 计划中出现过、被 Agent 拿掉的
   ```

3. 写第一版项目卡 Artifact，并渲染工作副本。
4. 生成工作目录：`AGENTS.md`、`.pi/mcp.json`。

项目库此后的 id 都向全局库申请（决定 2）。项目的 `AsOf` 与重放从根提交开始；更早的形成过程只能经外部引用访问全局库的历史。

## 6. Merge：两个方向

两个方向都是单父提交，不做三方自动合并（备忘 §6.1）。合并提交记 `merged_from`：

```yaml
merged_from: {store: global, from: commit_000032, to: commit_000040, nodes: [...]}
```

### 6.1 全局 → 项目（吸收更新）

| 步 | Agent | 中间件 |
| --- | --- | --- |
| 1 | 决定吸收到哪个全局提交 | `Diff(上次的来源提交, 目标提交)`，在全局库上求 |
| 2 | — | dry_run：把差异分成三类：<br>• 涉及项目成员或上下文的变化，候选吸收；<br>• 新出现的、与成员有关系的对象，候选纳入，附关系；<br>• 其余，不涉及项目 |
| 3 | 对候选逐项决定吸收、纳入或不要，写理由 | 对决定吸收的每项核对改前值：一致就应用；不一致记为冲突 |
| 4 | 对冲突交一份 graph-doc 作为决议 | 决议走 Commit 的检查 |
| 5 | — | apply：一个合并提交，更新 `origin` 之后的"上次来源提交"，重新渲染项目卡生成区 |

"全局撤回"（备忘 §5.2）作为普通的删除变化进入第 2 步，由 Agent 决定在项目中是否也删除。

### 6.2 项目 → 全局（回流）

| 步 | Agent | 中间件 |
| --- | --- | --- |
| 1 | 选定要回流的对象 | `Diff(项目根, 项目头)`，限定在选定对象上 |
| 2 | — | dry_run：把差异写成 graph-doc，在全局库上走 Commit 的 dry_run，包括查重（项目与全局可能各自建了同一个对象）、端点校验与 `confirm`；Artifact 另行处理（下文） |
| 3 | 答复阻塞项：同一性判断、端点补齐 | — |
| 4 | — | apply：全局库上的一个合并提交 |

规则：

- **选择不是删除**（备忘不变式 7）。差异从项目根算起，"未选入"不会出现。
- **项目内移除默认不回流。** 要回流时由 Agent 逐项显式列出；是否允许，见 §10。
- **Artifact 的回流走机制层的路径。** Commit 不能新建 Artifact，而项目中产生的 Artifact 往往最值得回流。Merge 按原样搬运 Artifact 节点、它的 `USED` 边与文档登记：
  - 文件按哈希核对；
  - 因为 id 统一分配，搬运不需要改写 id；
  - 指向未回流对象的 `USED` 列为阻塞项，Agent 选择一并回流，或不回流该 Artifact。
- **项目卡不回流。** 它记录的是项目本身。需要长期留存的结论，由 Agent 写成 Observation 回流；Observation 的 `ABOUT` 可以指向项目卡 Artifact，这时项目卡作为 Artifact 一并回流。

## 7. 中间件需要新增的能力

### 7.1 graph-vc

- 根提交带 `origin`，合并提交带 `merged_from`。二者都是提交记录上的机制层字段。
- `allocate_ids` 可以委托给另一个实例（全局库）。
- 应用变更集时，逐项核对改前值，返回冲突而不是整体失败（备忘 §6.1）。

### 7.2 E09 工具

| 工具 | 形式 | 用途 |
| --- | --- | --- |
| `Fork` | dry_run / apply | §5.2、§5.3 |
| `Merge` | dry_run / apply，参数 `direction: pull \| push` | §6 |
| `RecordCard` | 一次调用 | 把工作副本记录为新的项目卡 Artifact（§4.1）；工具名待定 |

渲染项目卡生成区的时机：Fork、Merge、RecordCard 之后。另可提供一个只渲染、不记录的入口，名称待定。

### 7.3 一个工作目录连接两个库

项目目录中的 Agent 需要：

- 读写项目库：日常工作；
- 读全局库：Merge 的 pull、比较项目与全局；
- 写全局库：Merge 的 push。

候选做法有两种：

- **(a) 一个 MCP 服务连接两个库。** 读取工具与读取接口加可选参数 `store: project | global`，默认 `project`；写入工具只写项目库，push 只经 `Merge`。
- **(b) 登记两个 MCP 服务。** 工具数翻倍；在 pi 的 direct 方式下，工具都直接列给模型。

倾向 (a)，待定（§10）。

## 8. 不变式与检验

沿用备忘 §8，本设计相关的有：

| # | 不变式 | 检验 |
| --- | --- | --- |
| 6 | **分支隔离：** 一个项目库的写入不改变其他库 | 各实例独立；检验 Merge 之外不会跨库写入 |
| 7 | **选择不是删除** | push 的差异中没有"未选入"引起的删除 |
| 8 | **约束保持**：含 Fork 与 Merge | 物化与合并后，端点、作用域、材料可读 |
| P1 | **闭合：** 项目库中每条关系的两端都在项目库中，或在 `origin.external` 中 | Fork 与 Merge 后检查 |
| P2 | **来源可复现：** 由 `origin` 与全局库的历史，能重新得出项目的根状态 | 重新物化并比较 |
| P3 | **id 唯一：** 各库中同一 id 指同一对象；不同对象不共用 id | 跨库检查 |
| P4 | **项目卡标明状态：** 每版项目卡记录它对应的提交；工作副本的修改与卡的落后都可检测 | §4.1 的检查 |

这些性质都不说明选择是否充分、项目卡是否忠实。那是任务层评测的问题。

## 9. 与评测的关系

- **基线。** 以 AGENTS.md 加文件系统作为项目记忆，正是"Agent＋文件系统"基线的具体形式：Agent 自己在 AGENTS.md 中记项目知识，没有来源、版本与隔离。与之比较，可以把收益限定在同一个入口（AGENTS.md）之后有没有带版本的状态，而不是"有没有项目记忆"。
- **候选观察点：**
  - Fork 计划的闭合与规模；
  - Agent 交代理由的完整度；
  - 项目卡落后或有未记录修改时，Agent 能否发现；
  - 试探线之间的干扰；
  - Merge 的冲突与查重；
  - 回看旧状态时，能否读到当时的项目卡与依据。
- **部署。** 每个项目一个 Neo4j 实例，评测时用镜像部署，以控制环境与复现。

具体任务与质量标准写入评测草案，待商定。

## 10. 待定问题

1. 闭合规则的具体范围：例如 Experiment 是否带上与它比较的基线方法的其他实验；Artifact 的 `USED` 默认展开还是默认改为外部引用。
2. 外部引用 `store@commit::id` 在 graph-doc 中的写法与解析；项目内写入引用外部 id 时的行为。
3. §7.3 采用 (a) 还是 (b)。
4. 项目内移除是否允许回流，怎样显式列出。
5. 全局卡是否进入全局库的版本历史。
6. 项目卡生成区的大小上限与超限时的写法。
7. 项目卡记录的时机：只由 Agent 调用 `RecordCard`，还是在 Merge 时也自动记录一次。
8. skill 的写法：步骤的粒度，何时停下来问用户；skill 本身的版本是否要记进项目卡或提交记录。
9. 项目实例的登记方式：名称、端口、凭据放在哪里，由谁维护。

## 11. 实现顺序（候选）

1. **graph-vc：** 根提交与 `origin`、`merged_from`、委托分配 id、改前值核对返回冲突，各配测试。
2. **项目实例：** 小堆配置的 compose 模板与登记方式。
3. **Fork：** dry_run 闭合检查、apply 物化、项目卡与工作目录的生成。
