# 评测草案

> **状态：** 草案，供讨论。本文把 intro 草稿的四个 challenge（C1–C4，见 `paper/narrative-draft.md`）落实为可操作的评测设计。§3–§6 的 e09 种子数据（`data/raw/e09-paper-knowledge/`）实例用于协议试点，不能作为独立正式测试集。模型见 [Graph Model V2](./graph_model_v2.md)，算子见 [算子契约](./operators.md)。任务集、金标准标注范围与 judge 协议尚未确定，确定前不实现 benchmark。

## 1. 评测定位与原则

评测的首要对象是**中间件的支持能力**，而不是下游任务分数；下游任务结果是应用证据。沿用项目既定原则：

- **能力对比可操作化。** 区分原生支持、经组合支持、需外部推理或额外实现支持。特性表不构成正确性或效率证据。
- **宣称与核验分离。** 论文宣称、仓库观察、运行成功、实验复现是不同发现，证据不足时保留不确定。
- **构建成本计入复用收益。** 复用节省必须和构建、维护成本放在同一本账上。
- **两套评测分开。** 同一份已构建知识上的受控对比（隔离使用阶段）与全流程构建+使用的对比（含构建质量与成本差异）回答不同问题，分别报告。
- **金标准与 rubric 在跑实验前冻结。**
- **主张与评测对齐。** 论文主张限定在所评测的工作负载类（多步、跨论文、跨 session、条件敏感的研究工作）上；通用单轮 QA 不作为主场任务，该类任务上与 RAG baseline 打平不反驳主张，也不在其上主张提升。
- **评测材料公开。** 任务定义、金标准、rubric 与运行轨迹随论文公开，可复现——AgenticScholar 未公布评测集是其被质疑点之一，公开是我们的区分点。
- **区分三种规模。** 语料/知识对象数、单项目的写入与历史长度、独立项目任务数分别决定系统规模、积累效果与结论的外推范围；不能用一种量替代另外两种。

## 2. 总体框架

三层评测，每层回答不同问题：

| 层 | 回答的问题 | 手段 | 是否需要 LLM judge |
| --- | --- | --- | --- |
| 能力层 | 机制本身对不对：身份与引用校验、契约拒绝、谱系可达、条件存活 | 确定性检查、负例测试 | 否 |
| 任务层 | 复用是否带来提升：有/无积累（或不同 baseline）下 agent 完成研究任务的成本与质量 | 受控任务对比 | 是（+人工抽检） |
| 成本层 | 复用收益是否抵过构建与维护开销，盈亏平衡点在哪 | 全账本统计 | 否 |

Baseline 三个，与 intro 草稿一致：

1. **裸 Neo4j + 手写 Cypher**——检验"通用后端加合适查询就够了"这一反驳；
2. **RAG**——naive vector RAG over `papers/*.md`（即种子中 `mc_naive_rag` 的定义；embedding 可用 `infra/vllm-qwen3-embed`），作为无结构积累的参照；
3. **Agent + 文件系统**——可持续写入的自由笔记，并评估带 Git 历史的配置。不能默认文件系统对照组每轮失忆。

公平性约束：所有 baseline 访问同样的材料、调用同样的模型、声明同样的预算。评测审计绕过中间件直接读源材料的行为，但不禁止。

### 2.1 任务分臂：按 reuse 的必要性组织

任务层的核心问题是"reuse 是否值得"。把它拆成两个子命题：命题 A（效率）——复用省掉的成本大于构建与维护成本，由成本账本（§7）回答；命题 B（质量）——在条件与证据起决定作用的任务上，有积累的回答更对，由任务层回答。任务按复用的必要性分为三臂，质量与成本分别报告：

| 臂 | 定义 | 实例 | 待检验的差异 |
| --- | --- | --- | --- |
| 历史依赖型 | 正确答案依赖前轮产物或特定历史状态 | Session 2 承接 Session 1 的比较表与判断；旧版本状态读取 | 比较各组是否保存并找到正确状态、付出多少代价 |
| 条件敏感型 | 答案正确性依赖实验条件随组合被正确使用 | $L=512$ 迁移判断（§4.2）；own/rerun/cited 判别（§4.3） | 比较条件与来源误读率；不预设对照组必然出错 |
| 效率型 | 各组可能都能答对，差异在成本 | ETTh1 跨论文比较（§3.2） | 看质量、成本差与盈亏平衡 |

参照系说明：AgenticScholar 的 reuse 证据只覆盖成本侧（计划复用降开销 >90%，其 Table 8），未做任务质量归因（无"无复用"对照臂），且 KG 构建成本不入账。我们的分臂设计同时回答成本与质量两个子命题，是对这一缺口的直接回应。

### 2.2 公开任务与语料的用途

目前没有一个现成 benchmark 同时覆盖论文知识、Agent 生成的产物、持续写入、项目视图和版本历史。正式评测应把外部任务与材料作为真实性和独立性的来源，另定义针对中间件的状态与操作序列：

| 来源 | 可使用的部分 | 不足与使用方式 |
| --- | --- | --- |
| [AstaBench：ArxivDIGESTables-Clean](https://github.com/allenai/asta-bench/blob/main/README.md#available-tasks) | 跨论文制作结构化比较表；可提供真实的 use-artifact 任务和参考产物 | 原协议未检验跨 session 复用与版本演化；改造为连续任务后须作为**新工作负载**报告，不能沿用官方分数 |
| [AstaBench：ScholarQABench2、PaperFindingBench](https://github.com/allenai/asta-bench/blob/main/README.md#available-tasks) | 外部给定的文献问答、检索任务，可作为后续使用的应用证据 | 分数混合了检索与 Agent 推理能力；先检查材料可获得性、任务间重叠和评价协议，不能直接当作中间件正确性指标 |
| [OpenAlex 数据快照](https://help.openalex.org/access/snapshot/) | 抽样构造更大规模的论文元数据和更新负载 | 元数据不提供本文所需的实验条件、判断与产物金标准；规模测试应和人工核验的语义任务分开 |
| [LongMemEval](https://github.com/xiaowu0162/LongMemEval) | 借鉴跨 session、知识更新和时间推理的任务形式 | 对象是对话记忆，不适合作为论文知识管理的主分数 |
| [LDBC SNB](https://ldbcouncil.org/ldbc_snb_docs/) | 借鉴读写混合负载和规模档位的设计方法 | 直接运行主要测图数据库后端，不覆盖本文的数据模型与算子语义 |

先从外部任务中筛选有可获取材料、可独立核验目标、且允许构造后续请求的实例；冻结筛选规则后再确定测试集。开发用种子和正式测试项目分离，按**项目或任务簇**划分而不是按单个问题随机划分，以防同一论文和产物跨集合泄漏。报告选入、排除的数量及原因；不得按正式结果挑题。

### 2.3 连续项目时间线：让“积累”成为可观测变量

每个独立项目由同一批固定材料和一串预先写定的请求组成。每轮结束 Agent session，但保留该条件下允许保存的数据状态；后续请求在前一轮执行时不可见。示例协议：

| 阶段 | 新输入与操作 | 主要检查 |
| --- | --- | --- |
| 初始构建 | 给第一批论文；入库知识并产出带输入依赖的比较表 | 写入与引用有效性、初始构建成本 |
| 跨 session 复用 | 给新论文或比较维度；扩展旧表并回答条件敏感问题 | 能否找到并正确使用已有对象和产物；避免重读的收益 |
| 更新与历史访问 | 固定一份新材料版本或修正一条记录；查询受影响产物，读取旧状态，并继续任务 | possible-staleness 指示、版本读取、修订成本；不预设自动语义重评 |
| 项目分化 | 若视图与分支契约已明确，从共同基线建立两个项目状态，分别继续写入 | 选择闭包、项目隔离、历史可见性；分支接口待定 |

比较组应从同样初始材料开始，使用同一通用 Agent、模型与预算，并分别保留各自按协议产生的状态。报告每轮的**数据库结果正确性**（对象、引用、依赖、视图与历史状态）、**下游产物质量**和**增量及累计成本**。记录 Agent 直接读取源材料的次数和代价；既不禁止，也不把绕过中间件所得的答案计作复用。另设“同一份已构建知识”的受控试验，以隔离构建质量与使用机制。正式负载应包含复用有利、收益不明显和可能有害的任务，不以预期胜负筛选。

### 2.4 三个独立的规模轴

- **语料规模：** 改变论文数、知识对象数与依赖边数，测构建成本、查询延迟、存储及更新代价；真实语义实例负责正确性，扩展或生成的数据只用于系统压力测试，并单独标注。
- **历史长度：** 改变每项目的提交数、产物数、依赖深度与材料更新次数，测历史读取、影响范围识别、维护开销和累计净收益。只增加论文数不能证明积累收益。
- **任务广度：** 增加相互独立的项目时间线和领域/任务类型，按项目报告分布与方差，而不是把同一项目的多轮请求当作独立样本。

规模档位与样本量须在材料可获得性和试点成本核查后确定，不能从两篇开发论文推断正式结论。通用单轮任务可用于适用边界检查；主张仍由上述连续管理负载支撑。

## 3. C1：复用单位与身份

**评测问题：** 跨论文的共同对象能否被赋予稳定身份并被后续工作直接引用？复用是否真实发生且正确？

### 3.1 能力层：身份判断的正确率

e09 论文文档开头的 `confirm` 块提供试点参考答案：写入 DLinear 时 `$dlinear` 被判为不同于 `method_0008/0007/0002/0004/0010`，PatchTST 的方法被判为不同于 `method_0004`（Transformer-based TSF 类别）。种子的撰写约定提供了判定规则（上下位概念不作别名；Llama-3-70B 与 Llama-3.3-70B 分开建节点；`2Wiki` 需结合上下文确认后再复用）。正式测试需要独立标注的身份判例。

- **任务：** 给 agent 查重候选列表，输出归并/区分决策。
- **指标：** 决策准确率，按"归并"与"区分"分别报告。
- **责任边界注意：** 语义判断在 Agent 侧，这里评的是模型与契约能否表达并校验身份，不宣称中间件自动做实体链接。

### 3.2 任务层：两段式复用协议

- **Session 1（构建）：** agent 将 DLinear、PatchTST 抽取入库（即现有 docs 03/04 的构建过程）。
- **Session 2（复用）：** 具体研究问题实例：

  > 在 ETTh1 上 horizon $T=720$ 时，DLinear 和 PatchTST 各自报告了什么结果？两个实验的 look-back 设置和切分约定一致吗？

  正确回答需要经共享节点 `dataset_0002`（ETTh1）把 S5.T3 与 S4.T3 接到一起，并对齐 $L=96$、Autoformer 切分约定等条件。

- **指标：**
  - 复用率：Session 2 产物中引用已有记录的比例 vs 重新抽取/重读 `papers/*.md` 的比例——"复用真的发生了"的直接证据；
  - 成本：token、wall-clock、工具调用数；
  - 质量：rubric 评分（覆盖度、数值正确性、条件忠实度），独立评审，judge 不知道产物来源；
  - 引用正确性抽检：引用是否指向真正支持该陈述的证据（防止幻觉式引用）。
- **对照：** 无积累的 RAG；能保留笔记的文件系统；带等价对象和查询实现的裸 Neo4j。分别报告“有无积累”的效应与“如何管理积累”的效应。
- **消融：** 共享身份 vs 每论文独立记录（字符串级对齐），测跨论文对齐任务的正确率差。

## 4. C2：组合中的条件与证据

**评测问题：** 多步组合（extract → matrix → report）后，条件、证据、输入依赖是否完整可回溯？契约校验能否拦住坏计划？

### 4.1 能力层

- **契约负例测试：** 提交结构错误、引用悬空、类型不符的计划与产物，测拒绝正确率。
- **谱系审计：** 对最终产物的已声明输入沿 `USED` 回溯，检查其所指对象和材料是否可达；再单独抽检产物陈述（如 `5.1 Experimental Settings::148:172` 对应的结论）是否真正受到原文支持、相关条件是否写进产物。输入级谱系不等于陈述级证据链，二者分别报告；不得把未声明的支持关系算作中间件保证。
- **材料变更：** 修改一份源材料，检查依赖产物是否出现 possible-staleness 指示。

### 4.2 任务层：条件迁移判断

具体任务实例：

> 我要在一个新的电力数据集上做 LTSF，可以用 $L=512$ 的长历史。DLinear 论文说大 look-back 窗口有效，我可以直接引用这个结论吗？

答对需要 S5.T4 上挂着的条件与 note：**DLinear 用 $L=336$ 而 FEDformer/Autoformer 保持 $L=96$**（不对称比较）；ILI 行 horizon 标签疑为误印（966 步的 ILI 不可能有 $T=720$）。

- **对比条件：** 带完整条件与 note 的记录 vs 裸结论（"大 look-back 下 DLinear 更优"）。
- **指标：** 迁移决策正确率、理由的条件忠实度；检验完整条件记录是否改善结果，不预设改善幅度或显著性。

### 4.3 任务层：宣称与核验的区分

S5.T2 的 EVALUATES 边将结果来源区分为 own / rerun / cited / unstated 四级（FEDformer 等六行数值 taken from the FEDformer paper，`source_refs` 指到原文第 172 行）。具体任务实例：

> DLinear 在 Weather 上胜过 FEDformer 的数值，是 DLinear 作者自己跑的吗？

正确答案是否定，并能给出行号依据。

- **指标：** 来源类型识别正确率；进一步测结论强度标注是否与证据来源一致（cited 的结论不应被当作独立复跑）。

### 4.4 消融

去掉契约校验，观察多步组合后产物证据完整率的衰减（回应"校验是否值得"）。

## 5. C3 / C4：待细化的状态评测

连续项目时间线（§2.3）的更新与分化阶段为 C3/C4 提供共同负载。能力层需要给定一串明确的写入和预期状态，逐次核对视图选择闭包、required context 完整性、提交记录完整性、历史读取与项目隔离；任务层检查 Agent 能否在指定项目状态下找到正确产物并继续工作。产物的输入谱系与知识状态的提交祖先须分别判定。视图选择、分支与集成的具体实例和判据待契约确定后补齐；未实现的接口不能计入已验证结果。

## 6. 端到端场景

完整重演 intro Figure 1 的场景作为协议试点与定性 demo；这两条线路来自开发种子，不能代替独立正式测试项目：

- **TSF 线：** Session 1 读 DLinear + PatchTST；Session 2 带新需求回来（"设计在 ETT 上超越 PatchTST 的对比实验方案"），选取已有记录、复检条件、补读第三篇（如 iTransformer）并修订比较。
- **RAG 线：** GraphRAG → LightRAG → HippoRAG → HippoRAG2 构成"从检索到记忆"线路，共享 MuSiQue / HotpotQA / LV-Eval / 检索器模型节点；LV-Eval 的"数据集 × 长度级别"与 MuSiQue 的 Ans/Full 版本区分是现成的 C2 条件测试点。

两条线路共享种子机制但内容独立，同时支撑 C3 横向选择继承的评测。

## 7. 成本账本

- **构建成本：** Session 1 的 token、时间、人工校验量；
- **复用节省：** Session 2 相对无积累对照的成本差；
- **维护成本：** 材料变更后的复检开销；
- **报告：** 盈亏平衡点（第几次复用开始净收益为正）。这是回应"为什么不直接 RAG"的关键数字。
- **时间线口径：** 每轮分别报告增量成本与累计成本，包含失败调用和材料直读；盈亏平衡须基于全流程对照计算，不能只比较最后一轮的 token。

## 8. 待定项

1. **任务集与金标准：** §3.2、§4.2、§4.3 各任务实例需要冻结的标准答案（数值、条件、判据），标注粒度与标注人待定；
2. **RAG baseline 配置：** chunk 大小、embedding 模型、top-$k$；
3. **judge 协议：** 人工、LLM 还是混合，rubric 细则。约束已定的部分：judge 与被测系统骨干不同源、多骨干复跑、报告方差与显著性、人工抽检比例写死——针对 AgenticScholar 同源裁判、无方差报告的教训；
4. **统计口径：** 复用率与成本从哪个日志层面统计（候选：pi session 的工具调用 trace）；
5. **正式任务来源：** 先核查 ArxivDIGESTables 等公开任务的材料、许可、目标与项目簇划分；确定可用于原协议对照的子集，以及需要改造成连续时间线的新任务。改造后的结果与官方 benchmark 分数分开报告；
6. **时间线金标准：** 每轮输入、预期对象与状态、产物可接受答案、材料变更和未来任务隐藏规则；C3/C4 的视图及分支实例待契约明确；
7. **规模与样本量：** 语料规模、历史长度、独立项目数分别设档；两篇 TSF 论文与 RAG 种子只做试点，正式项目、统计单位和成本预算待定。
