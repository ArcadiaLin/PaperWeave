## 1. 评测要回答的问题

### 1.1 为什么换骨架

评测的作用是把系统设计变成一个可以被证明或证伪的问题。只有这样，它才能帮我们决定该在哪些任务上下功夫，而不是逐项堆砌功能。

旧版评测按身份、条件、视图、历史逐项检查，每一项都能通过，但合在一起得不出结论。审稿人会追问 so what。语义模式、算子系统、版本与视图这三项工作分开评测都偏弱：

- 模式本身没法单独评测，只能看它支撑了什么；
- 版本和视图单独评测，只是逐项打勾。

所以它们都需要挂在同一个命题下。

### 1.2 主场与边界

最强的反驳是：**一个 Agent 用 markdown 文件加 git 就够了。** 在单个 Agent、单个项目、几十篇论文的场景里，这个反驳大概率成立；即使数据库有优势，也可能抵不过构建成本。评测不把主场设在这里。我们把这个场景作为边界条件如实报告，不回避。

数据库思路站得住的场景是：**许多互不协调的 Agent 或 session，长期往同一个共享库里写入，也从中读取。** 这是项目最初 paper4agents“论文知识共享集散平台”的设想。这里的写者不需要协作，也不需要专门的多 Agent 工作模式。数据库的传统存在理由正是共享、长期存在、多写者多读者、需要完整性；在这种场景下，无约束的自由文本积累会出现以下退化：

- **重复：** 同一个对象被不同写者写成多个实体；
- **悬空：** 引用指向不存在或已被改动的对象；
- **未察觉的冲突：** 不同写者的判断互相矛盾，却没有人发现；
- **过时：** 产物所依据的材料或记录已经修订，没有人知道它需要复检。

### 1.3 中心命题

| 命题 | 内容 | 怎样算被证伪 |
| --- | --- | --- |
| **T1 退化（核心）** | 没有身份、契约、谱系与版本约束时，共享积累会随写者数和写入量增加而退化，下游正确率随之下降；这些约束能抑制退化 | 在写者数和写入量增长时，文件加 git 或无约束图库的退化斜率与完整系统没有可区分的差异 |
| **T2 摊销** | 结构化积累把成本从使用阶段挪到构建阶段，构建成本可以被许多使用者分摊 | 盈亏平衡点 $N^*$ 在合理的使用者数内不存在；或对照组拿到同等预计算预算后能获得同等收益 |
| **T3 能力平移（可选）** | 结构化接口能缩小弱模型与强模型之间的差距，使便宜的模型够用 | 在模型强度扫描中，用与不用中间件的差距不随模型强度变化 |

T1 是主实验。T2 用 T1 时间线上的成本账本回答，不另起实验。T3 只在资源允许时进行，方式是在 T1 和 L4 上换模型重跑。

**项目视图与版本历史不单独成节**，作为 T1 长时间线上的事件来评测（§4.4）：

- 不同写者群体之间的隔离，就是分支；
- 撤回或修订一条记录后，哪些产物受影响，就是历史查询与影响查询；
- 项目成果回流到共享库，就是多写者写入的一种路径。

### 1.4 评测原则

以下原则沿用项目既定规则：

- **先评中间件的支持能力。** 下游任务分数是应用证据，不是唯一或主要的度量。
- **能力对比要可操作。** 区分原生支持、经组合支持、需要外部推理或额外实现才能支持三种情况。特性表本身不构成正确性或效率的证据。
- **宣称与核验分离。** 论文的宣称、仓库中的观察、运行成功和实验复现是不同的发现；证据不足时保留不确定性。
- **两类评测分开报告。** 一类是在同一份已构建知识上的受控对比，隔离使用阶段；另一类是对构建加使用全流程的对比，包含构建质量与成本的差异。
- **公平对照。** 所有组访问同样的材料，使用同一通用 Agent（默认配置的 pi）、同一模型和同样的预算。评测审计绕过中间件直接读源材料的行为，但不禁止。
- **先冻结后实验。** 金标准、rubric 和筛选规则在跑实验前冻结，不按正式结果挑题。正式负载应包含复用有利、收益不明显和可能有害的任务，不按预期胜负筛选。
- **主张与负载对齐。** 主张限定在多写者、跨论文、跨 session、条件敏感的负载上。通用单轮问答只做适用边界检查：在这类任务上与 RAG 打平，不构成对主张的反驳，我们也不在这类任务上主张提升。
- **评测材料公开。** 任务定义、金标准、rubric 和运行轨迹随论文公开。AgenticScholar 没有公开评测集，这是它被质疑的点之一，公开评测集是我们的区分点。

## 2. 写者模型

### 2.1 什么是“互不协调的写者”

一个写者是一个独立的 pi session（或一串 session），带着自己的研究任务，读论文、抽取、比较、写产物。写者之间：

- 没有共同的计划，也不互相通信；
- 唯一的联系是共享库：彼此写入的内容通过它被看见；
- 读的论文有重叠，重叠程度是实验变量（§4.2）。

这个设定不要求写者同时写入。实验中**写者轮流执行**，让同一时刻只有一个写者在提交，从而把事务级并发排除在贡献之外（另见 §9 中提交锁外查重的问题）。我们要测的退化来自语义层面：不同写者对同一对象、同一结论各写一份，而不是来自并发写入的竞争。

### 2.2 两种写入路径

| 路径 | 含义 | 对应设计 |
| --- | --- | --- |
| 直接写共享库 | 写者经 `Commit` 和 Agent 算子把论文知识与产物写进全局库 | [提交契约](./commit_contract.md) |
| 项目回流 | 写者从全局库 Fork 出项目库，在项目内工作，再经 Merge push 把成果写回 | [项目视图](./project_views.md) §5–§6 |

第一种路径能测“多人往一个库里写”的基本退化。第二种路径把项目视图和版本历史放到多写者的场景中：项目内的隔离就是分支，push 时的查重与冲突就是多写者冲突在合并点的表现。两种路径用哪一种、是否都做，取决于 Fork 与 Merge 的实现进度（§9）。

## 3. 对照组

| 组 | 配置 | 回答的问题 |
| --- | --- | --- |
| **A0 文件加 git** | 共享一个 git 仓库，Agent 用 markdown 自由组织（可参照 llm-wiki 一类做法），允许自建索引、目录约定和 AGENTS.md；与 A3 的写回预算相同 | 最强的反驳：通用 Agent 自己能否维持共享积累的质量 |
| **A1 RAG** | 对论文原文做向量检索，并给它与 A3 同等的预计算预算（例如用同样多的 token 为每篇论文预先生成摘要笔记，一起入索引） | 无结构积累，但预计算预算相同 |
| **A2 去掉约束的图库** | 我们的系统关掉身份查重、契约检查与谱系记录，即“裸 Neo4j 加 Cypher” | 通用后端加合适的查询是否就够了 |
| **A3 完整系统** | 默认配置 | — |
| **消融** | 在 A3 上分别去掉身份、契约、谱系、版本 | 退化抑制分别来自哪项约束 |

对 A0 必须给最强配置，不能默认文件系统组每轮失忆。如果 A0 只在弱配置下输，T1 就没有说服力。A2 几乎不需要新工程，而且是“通用后端就够了”这个反驳最直接的检验。

## 4. T1 主实验：多写者积累时间线

以下是最小规约的候选，数值待试点后确定。

### 4.1 语料

- 选一个子领域，约 300 篇论文。候选领域是 LTSF，因为已有 TSF 种子论文和抽取经验；RAG/记忆领域可作为第二个领域，用于检验外推。
- 语料按发表时间排序，写者按时间顺序接触论文。这样 L4 的时间切分任务（§6）可以复用同一语料。
- 两篇 TSF 种子论文和 RAG 种子只做试点，不进入正式结论。

### 4.2 变量

| 变量 | 候选取值 | 作用 |
| --- | --- | --- |
| 写者数 $K$ | 1、2、4、8 | 主自变量；$K=1$ 是单 Agent 的边界条件 |
| 论文重叠率 | 低 / 中 / 高 | 控制不同写者撞上同一对象的频率 |
| 写入量 | 按检查点累计（如每接触 50 篇论文） | 横轴 |
| 写者任务 | 每个写者一条研究线路，如“为某类方法做比较表”“评估某个结论能否迁移” | 让写者产出不同的产物，而不只是重复抽取 |

### 4.3 度量

在每个检查点上测量，画成随写入量变化的曲线，并按 $K$ 分组。

**库的健康度（不需要 judge）：**

| 指标 | 定义 | 金标准来源 |
| --- | --- | --- |
| 重复实体率 | 同一现实对象（方法、数据集、指标、模型）在库中对应多个实体的比例 | 对实体对齐的抽样人工标注；数据集与指标可借排行榜标注做部分对齐（§7） |
| 误合并率 | 不同对象被合成一个实体的比例，例如上位概念被当作别名，或模型版本被混淆 | 同上；与重复实体率一起报告，避免只压低重复率 |
| 悬空引用率 | 引用指向不存在、已被改动或无法解析的对象的比例 | 确定性检查 |
| 冲突检出率 | 注入的、相互矛盾的记录中，被系统或下游 Agent 发现的比例 | 注入事件，金标准由构造给出 |
| 过时识别率 | 修订或撤回后，依赖它的产物被正确标为需要复检的比例；同时报告误报 | 注入事件，影响范围由依赖关系确定 |

**下游正确率：** 用一组固定的探针查询，在每个检查点上都跑一遍。探针取自能力阶梯的 L1 和 L3（§5），例如：

- “哪些论文在数据集 Y、条件 Z 下评测过方法 X”；
- “这份比较表当时依据的是哪些记录”；
- “这次修订影响了哪些产物”。

探针由一个固定的读者 Agent 执行。读者与写者分开，从而把“库的质量”与“读者的能力”分开衡量。

**结论形式：** 比较各组的退化斜率随 $K$ 的变化。如果 A0 的斜率与 A3 没有可区分的差异，T1 不成立。

**审稿人可能会问：** 加了约束更好，这不是理所当然吗？真正有信息量的是两件事：

- 文件加 git 在什么规模、什么重叠率下开始输；
- 输掉的部分具体来自哪种退化。

因此，曲线的拐点和消融归因比最终分数更重要。如果 A0 在我们能负担的规模内始终不输，这本身就是值得报告的结果，主张需要相应收窄。

### 4.4 注入事件：视图与版本在这里被评测

时间线上预先写定若干事件。事件对写者不可见，在指定检查点发生：

| 事件 | 做法 | 检查什么 |
| --- | --- | --- |
| 读错后修订 | 某写者的一条记录含一个错误数值，之后由另一写者发现并修订 | 修订能否被记录；依赖该记录的产物能否被找出；旧状态能否读回 |
| 撤回 | 撤回一篇论文或一条记录 | 影响范围查询的正确率与误报 |
| 材料变更 | 固定一份源材料的新版本 | possible-staleness 指示；不预设自动语义重评 |
| 分歧 | 两个写者对同一对象写出不同内容 | 分歧被拒绝、并存还是被裁决；是否留下记录（依赖 §9 第 1 项的设计） |
| 分支与回流 | 两条研究线路从同一基线 Fork，各自前进，再 push 回全局库 | 项目隔离、上下文闭合、push 时的查重与冲突、历史可见性 |
| 回看 | 查询某份早期产物在形成时依据的知识状态 | 历史读取正确性；区分产物的输入谱系与知识状态的提交祖先 |

原来 C3/C4 的能力检查（视图选择闭合、上下文完整、提交记录完整、项目隔离，见 [项目视图](./project_views.md) §8 的不变式）在这些事件发生后逐项核对，计入 L0/L3。

A0 组也会经历同样的事件。它可以用 git 的历史和自己维护的笔记去应对，我们比较的是应对的正确率和代价。

## 5. 能力阶梯 L0–L4

阶梯的作用是归因：下游效果提升时，能说清提升来自哪一层。它不是要求把所有能力都完整测一遍。

| 层 | 能力 | 金标准来源 | judge |
| --- | --- | --- | --- |
| **L0 存储语义** | 身份与引用校验、契约拒绝、谱系可达、版本读取、不变式 | 脚本化的写入序列与预期状态；负例测试 | 不需要 |
| **L1 关联检索** | 跨论文按对象和条件查找记录 | 排行榜类标注（§7），集合的精确率与召回率 | 不需要 |
| **L2 组合** | 跨论文比较表；条件随组合正确保留 | ArxivDIGESTables 的参考表；条件与证据抽检 | 部分需要 |
| **L3 有状态工作** | 跨 session 接续工作；修订后的影响范围；读取旧状态 | 脚本化（与 §4.4 的注入事件共用） | 基本不需要 |
| **L4 端到端** | 时间切分的实验设计任务（§6） | 后来发表的论文的实际实验设置 | 需要，并配人工抽检 |

旧版中基于 e09 种子的具体实例保留为试点用例，挂到对应层上：

- **L1/L2：ETTh1 跨论文比较。**“在 ETTh1、horizon $T=720$ 时，DLinear 和 PatchTST 各自报告了什么结果？两者的 look-back 设置和切分约定是否一致？”答对需要通过共享节点 `dataset_0002`（ETTh1）连接 S5.T3 与 S4.T3，并对齐 $L=96$、Autoformer 切分约定等条件。
- **L2：条件迁移。**“新数据集上可以用 $L=512$，能直接引用 DLinear 的‘大 look-back 有效’吗？”答对需要 S5.T4 上的条件：DLinear 用 $L=336$，而 FEDformer/Autoformer 保持 $L=96$，比较不对称；ILI 行的 horizon 标签疑为误印。
- **L1：宣称与核验。**“DLinear 在 Weather 上胜过 FEDformer 的数值，是 DLinear 作者自己跑的吗？”正确答案是否定的，FEDformer 等六行数值取自 FEDformer 论文，依据在原文第 172 行。这一例检验 EVALUATES 边上 own / rerun / cited / unstated 四级来源能否被正确使用。
- **L0：身份判例。** e09 论文文档开头的 `confirm` 块提供试点参考答案，例如 `$dlinear` 不同于 `method_0008/0007/0002/0004/0010`。

**责任边界：** 语义判断在 Agent 侧。L0 和 L1 测的是模型与契约能否表达、校验、找到这些判断，不宣称中间件自动做实体链接或推断矛盾。

## 6. L4 下游任务：时间切分的实验设计

PaperBench 不合适：它主要测写代码和复现结果的能力，知识库的作用很小，而且和编码能力混在一起。

**任务：**

1. 用时间点 $t_0$ 之前的论文建库。T1 时间线结束时的库可以直接使用，各组用各自积累出的库。
2. 取 $t_0$ 之后发表的目标论文，只给 Agent 它的研究问题和方法描述。
3. 要求 Agent 给出实验设计：应对比哪些 baseline，用哪些数据集和指标，已有结论在什么条件下成立。
4. 金标准是目标论文实际采用的实验设置，不需要我们另行标注。

**度量：** baseline、数据集、指标各自作为集合计算精确率与召回率；条件说明由 judge 评分并人工抽检；同时报告成本。

**这个任务能回应的质疑：**

- **缺乏对比：** 金标准来自外部，所有组在同一语料上运行，回应“自定义任务缺乏对比”。
- **收益来源：** 几百篇论文不可能在一次任务中逐篇读完，测到的收益只能来自关联与复用。这符合“评测要排除仅靠读原文就能得到的收益”的原则。
- **数据泄露：** 目标论文选在被测模型知识截止日期之后。

**已知局限：**

- 目标论文的实际选择不一定是最优选择，只是一个合理的参照。因此金标准只用于计算集合重合度，不把“与目标论文一致”说成“正确的科研决策”。
- 写者是否会在库中写入与目标论文高度相关的内容，取决于语料与写者任务的设定，需要在冻结任务前检查泄漏。

## 7. 金标准与公开数据的用途

目前没有现成 benchmark 同时覆盖论文知识、Agent 产物、多写者持续写入、项目视图与版本历史。外部数据用来提供真实性与独立性；状态与操作序列由我们针对中间件另行定义。

| 来源 | 可用的部分 | 不足与使用方式 |
| --- | --- | --- |
| TDMS（Hou et al. 2019）、AxCell、SciREX | 任务、数据集、指标、结果的标注，与 Experiment/Result 结构对应 | L1 探针与数据集、指标的实体对齐金标准；领域覆盖与能否获取要核查 |
| LEGOBench（`2024-LEGOBench`） | 基于 arXiv 与 PapersWithCode 超过 1.1 万个排行榜的排行榜生成任务 | 同上；规模大，可用于 L1 抽样；PapersWithCode 已停运，需确认归档数据的完整性 |
| SciLead（`2024-SciLead`） | 人工整理的 TDMR 排行榜，指出社区排行榜有大量不完整 | 比社区数据更可靠的 L1 金标准；规模较小 |
| [AstaBench：ArxivDIGESTables-Clean](https://github.com/allenai/asta-bench/blob/main/README.md#available-tasks) | 跨论文结构化比较表及参考产物 | L2 金标准；原协议不测跨 session 与版本，改造后作为新负载报告，不沿用官方分数 |
| [AstaBench：ScholarQABench2、PaperFindingBench](https://github.com/allenai/asta-bench/blob/main/README.md#available-tasks) | 文献问答与检索任务 | 仅作应用证据；分数混合了检索与推理能力，不当作中间件正确性指标 |
| MemoryAgentBench（`2026-MemoryAgentBench`）、[LongMemEval](https://github.com/xiaowu0162/LongMemEval) | 增量积累、知识更新、选择性遗忘等任务形式 | 借鉴 L3 的任务形式；对象是对话或长上下文记忆，不作为主分数 |
| ResearchBench（`2026-ResearchBench`） | 从论文自动抽取研究问题、背景与假设的方法 | 可借鉴 L4 目标论文的输入构造；它测的是假设发现，与我们的实验设计任务不同 |
| [OpenAlex 数据快照](https://help.openalex.org/access/snapshot/) | 大规模论文元数据 | 只用于规模压力测试和 T2 的粗略估算；元数据不提供语义金标准 |
| [LDBC SNB](https://ldbcouncil.org/ldbc_snb_docs/) | 读写混合负载与规模档位的设计方法 | 只借鉴设计方法；直接运行主要是在测图数据库后端 |

**筛选规则：**

- 先从外部数据中筛出材料可获取、目标可独立核验的实例，冻结筛选规则后再确定测试集。
- 开发种子与正式测试按项目或任务簇划分，不按单个问题随机划分，以免同一论文或产物同时出现在两个集合中。
- 报告选入与排除的数量及原因。

## 8. T2 成本账本与其他度量

### 8.1 成本账本

成本分项记账，在 T1 时间线的每个检查点同时报告增量和累计值，失败的调用和对原文的直接读取都要计入：

- **构建：** 抽取与入库的 token、时间，dry_run 来回轮数（`IngestBatch` 已有统计）；
- **写回：** 产物写入与契约校验的额外开销；
- **使用：** 每次下游任务的成本；
- **维护：** 修订、撤回、材料变更之后的复检开销。

盈亏平衡点：

$$
N^* = \frac{C_{\text{build}}}{c_{\text{base}} - c_{\text{ours}}}
$$

其中 $C_{\text{build}}$ 是构建与维护的总成本，$c_{\text{base}}$ 与 $c_{\text{ours}}$ 是对照组与我们每次使用的成本。

**对成本的三种合理表述：**

1. **写回开销。** 知识积累是 Agent 正常工作的副产品，它本来就要读论文。我们报告的是相比“只读不写”多花了多少，而不是整个库的构建费用。这是最诚实的表述。
2. **摊销。** 共享库由许多使用者分摊，$N^*$ 随使用者数增加而变得容易达到。**前提是对照组拿到同等的预计算预算**（§3 的 A1）。否则差异可能只来自“我们做了预计算而对照组没做”，这个论点会被直接驳回。
3. **离线与在线用不同模型。** 构建阶段用便宜模型，使用阶段用强模型，与 T3 呼应。

用 OpenAlex 年度快照或一年的会议论文总量估算平台级成本，只放在讨论部分作为粗略估算，不作为主要证据。

### 8.2 Agent 是否用得顺手

这些指标必须和正确率一起报告，因为用得顺手不等于结果正确：

- **交互效率：** 工具调用次数、无效调用率、dry_run 来回轮数；
- **显示偏好：** Agent 保留了文件与 shell 权限，我们只审计、不禁止它绕过中间件。它多常绕开中间件、直接读原文，本身就是“好不好用”的证据。绕过所得的答案不计作复用；
- **模型强度扫描：** 即 T3。

### 8.3 规模的三个维度

- **语料规模：** 论文数、知识对象数、依赖边数，决定系统的规模。真实语义实例负责正确性；扩展或生成的数据只用于压力测试，并单独标注。
- **写者与历史：** 写者数 $K$、每条时间线的提交数、注入事件数，决定积累效果。只增加论文数不能证明积累收益。
- **任务广度：** 独立时间线和领域的数量，决定结论能外推多远。按时间线报告分布和方差，不把同一时间线上的多次查询当作独立样本。

## 9. 运行 T1 之前需要先解决的工程问题

1. **内容分歧会被整批拒绝（最关键）。** 提交契约 §5 规定：实验、主张或贡献的内容有变化即为冲突，整批拒绝；当前不做修订和撤回，需要时清库重建。单写者时这种情况很少，多写者时会频繁出现，而且正是 T1 最常走的路径。分歧如何并存、由谁裁决、记录成什么，需要先讨论定下来；否则完整系统会表现为“大量写入被拒，Agent 不知道怎么办”。§4.4 的修订、撤回、分歧三类事件都依赖这项设计。
2. **查重在提交锁之外。** `prepare` 中的查重不在 graph-vc `_commit` 的锁内，两个写者同时新建同一对象时可能都会成功。这一点只读了代码，未实测。实验采用轮流写入的方式，可以先绕开。
3. **Fork 与 Merge 尚未实现。** [项目视图](./project_views.md) 已有设计，但未实现。在实现前，T1 只能走“直接写共享库”的路径，§4.4 的分支与回流事件推迟。
4. **评测运行框架。** A0、A1、A2 的配置，多写者调度，注入事件的脚本，检查点上的探针执行，以及时间切分任务的数据准备。这些属于评测工程，不改变系统本身。

## 10. 风险与可能的负结果

- **A0 不输。** 在可负担的规模内，文件加 git 的退化斜率与完整系统相当。这时应报告文件加 git 足够的区间，把主张收窄到更大规模或更高重叠率的场景，而不是换一个对我们有利的负载。
- **约束的代价超过收益。** 契约校验与拒绝导致写回成本过高，Agent 频繁绕开中间件。显示偏好指标会直接暴露这一点。
- **退化只来自某一项约束。** 如果消融显示只有身份查重有效，其余约束不起作用，论文主张应相应收缩。
- **judge 的偏差。** L4 依赖 judge 打分。judge 与被测系统的骨干模型不同源，用多个骨干复跑，报告方差与显著性，人工抽检比例事先固定。这是吸取 AgenticScholar 用同源裁判、不报告方差的教训。
