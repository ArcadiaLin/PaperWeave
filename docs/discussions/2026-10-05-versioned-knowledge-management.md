## 1. 定位

我们不研究如何优化版本控制，而是让学术资源管理系统支持版本管理，并提供有用的配套机制。版本管理服务于两件事：

- **全局与项目两个范围的知识管理。** 项目从全局库的某个固定状态选取知识、组织上下文，之后在本地使用和积累，再显式地吸收全局的更新，或把成果回流到全局。
- **让 Agent 的知识持久化过程可追溯。** 对某个对象的理解如何形成和修改、由谁写入、依据什么、做过哪些同一性判断，都可以按时间顺序查询。

版本存储和分支本身不构成新颖性。值得研究的候选问题是：在项目选取与独立演化中，能否维持语义身份、来源记录、Artifact 输入与材料版本之间可解释的一致性，并用可组合的操作支持这些状态的建立、使用和更新。这仍是待论证的方向。

## 2. 基本概念

### 2.1 版本化的对象是联合状态

提交 $c$ 下的逻辑状态记作

$$
S_c=(K_c,V_c,M_c,\Sigma_c).
$$

- $K_c$：知识记录、Artifact 及其关系；
- $V_c$：项目成员、局部绑定与可见范围；
- $M_c$：材料与 Artifact 文档的固定版本引用；
- $\Sigma_c$：解释这一状态所需的 schema 版本与契约版本。

这里的要求是：给定一个状态，就能确定它的含义和内容。如果图恢复到了旧提交，读到的却是最新的成员表或最新的文档，得到的就是新旧混合的状态。文件内容可以存放在图外，但旧引用必须仍能读到对应的字节。

### 2.2 五种关系彼此独立

| 关系 | 含义 | 不能推出 |
| --- | --- | --- |
| 领域语义关系 | 方法、实验、主张、判断及其范围 | — |
| Artifact 输入谱系（`USED`） | 产物声明用了哪些对象、记录和材料 | 完整推理过程，或判断为真 |
| 项目初始化来源（`origin`） | 项目从哪个全局状态、按什么选择构造而来 | 不必转成普通的父提交 |
| 提交祖先（`PARENT`） | 初始化之后，哪些提交建立并改变了状态 | 同一提交改了 A、B，推不出 B 的内容依赖 A |
| 物理恢复关系 | 从哪些快照、增量或对象块恢复一个状态 | 不改变以上任何逻辑含义 |

### 2.3 三个容易混淆的“提交”

| 名称 | 是什么 |
| --- | --- |
| Commit 工具 | 外部 Agent 交 graph-doc 的写入入口（dry_run / apply） |
| 后端事务 | 数据库一次原子写 |
| 提交对象（Commit） | 版本历史中的一条记录，本文的主角 |

三者可以一一对应，但不能因为名称相同就默认是同一个东西。

## 3. 提交

### 3.1 统一的写入底层

所有对状态的修改都经过同一个底层：输入一份解析后的**变更集**，在单个事务中修改图、写入提交对象并推进分支头。上游有两种写入流程：

- **Commit 工具：** graph-doc 经 dry_run 得到变更集；
- **Agent 算子：** 校验通过后写 Artifact。

此外，`Fork`、`Sync`、`Promote`、`Revert` 也都通过生成变更集、交给这个底层完成。

### 3.2 提交对象记录什么

| 内容 | 作用 |
| --- | --- |
| 输入原文（graph-doc 或算子调用参数） | 记录写入者想要什么；也用于评估 Agent 的行为 |
| 变更集 | 实际生效的修改（见 3.3），是版本数据的本体 |
| `parent` | 单父；项目根提交没有父提交，改记 `origin`（第 5 节） |
| `branch`、`base` | 写到哪条分支；写入者读视图时所在的提交 |
| `by`、`at`、`source` | 写入者、时间、来源（Commit 工具，或某个 Agent 算子及其产出的 Artifact） |
| `message` | 为什么这样改。改前值与改后值只能说明改了什么，说明不了原因 |
| `confirm` | 写入时的同一性判断（如 `distinct_from`）、删除确认等。它们不进入学术层，但属于这次写入的依据 |
| `rounds` | dry_run 的来回轮数，用于统计构建成本 |
| `ids` | 临时引用到 id 的映射 |
| `touched`、`removed` | 本次新建或修改的节点、删除的节点；作为索引，供 `Log` 过滤和 `Diff` 圈定候选 |
| `schema` | graph-doc 格式与 schema 的版本（$\Sigma_c$） |

### 3.3 变更集

- **节点：** `create` 记改后值；`update` 逐个属性记改前值和改后值；`delete` 记被删节点的全部属性。
- **边：** 以起点、类型、终点标识一条边，按 `create`、`update`、`delete` 记录边属性的改前值和改后值。删除节点时，它连着的边逐条记入。
- **名称与材料：** NameKey 的注册与撤销；Material 的路径、哈希和归属。
- **派生字段：** 自然键、向量等可以从数据重算的字段不记录，重放时重新计算。
- **记录的是逻辑变化。** 压实、重建索引、重新物化都不产生提交，也不能在 `Diff` 中显示为知识变化。

带改前值的变更集有两个用途：一是可以逆向执行；二是把它应用到另一个状态时，可以逐项核对前提是否成立（第 6 节）。

### 3.4 跨图与文件的原子性

材料和 Artifact 文档存放在图外。候选协议如下：

1. 先写入按内容寻址、不可变的文件；
2. 再在一个事务中校验文件存在且哈希一致，然后发布图修改、提交对象和分支头；
3. 没有被任何成功提交引用的文件，之后统一清理。

这不等于实现了跨存储的分布式事务。真正要保证的是可见性不变式：只要一个提交可见，它引用的文件就全部可读。

## 4. 历史读取

对提交 $c$ 上项目 $p$ 的逻辑状态 $S_{p,c}$，若一个查询 $q$ 受该状态支持，候选语义为

$$
\operatorname{ReadAt}(p,c,q)=q(S_{p,c}).
$$

无论采用哪种物理组织（全量复制、增量、检查点、对象共享），这个结果都应当相同。

| 算子 | 作用 |
| --- | --- |
| `Log` | 按时间列出提交；可按分支、写入者、来源、时间、触及的节点过滤 |
| `Show` | 显示一个提交的完整记录 |
| `Diff` | 求两个状态之间的逻辑差异，以 graph-doc 的形状给出。实现时先找共同祖先或来源基线，再取两侧 `touched ∪ removed` 的并集，只比较这些节点 |
| `AsOf` | 在某个提交时，一个节点或子图的状态 |
| `Blame` | 每个属性、每个关系键最后由哪个提交写入 |
| `Revert` | 把一个提交的逆向变更集作为新提交写入，不改写历史 |

这些都是机制层算子。学术层的 Search、Traverse 默认不返回提交对象。

## 5. 项目的建立

### 5.1 Fork：选取，而不是克隆

`Fork(source, selection)` 从全局库的固定提交出发，选取知识、组织上下文，然后建立项目的**根提交**：

- 根提交存储初始化后的完整状态（全量快照，或一份完整的初始化变更集），保证项目起点可以恢复；
- 根提交不把全局提交接为父提交，而是记录 `origin`：来源分支与提交、选中的对象及其版本、选择依据、摘要 Artifact 及其输入范围、外部引用清单、未纳入内容的说明；
- 项目自己的 `AsOf` 与重放都从根提交开始；更早的形成过程只能经明确保留的外部历史访问。

继承知识状态与继承形成历史是两个独立的选择：项目可以只继承对象当前选定的状态，而不带上它们的全部历史和所有上游论文。

在同一个项目状态上分出试探线，用 `Branch(base)`。两条线起点相同，之后的写入互不影响。

### 5.2 三种“不在”

| 情形 | 含义 | 机制 |
| --- | --- | --- |
| 未选入 | 初始化时的选择结果 | 不出现在项目历史中；回流时不会变成删除 |
| 项目内移除 | 项目显式删除了某个对象 | 项目分支上的普通删除提交；回流时是否传到全局，需要显式决定 |
| 全局撤回 | 全局库显式删除了某个对象 | main 上的删除提交；`Sync` 时作为普通变更进入项目，可能产生冲突 |

这三种情形不能靠一次集合求差来猜测。由于项目以根提交开始，从项目根到项目头的差异中天然不包含“未选入”。

### 5.3 上下文闭合与跨范围引用

选入一个对象时，它依赖的上下文要按约定能够解析，而不是把所有传递依赖无限展开、全部复制进来。可选的处理方式：

| A 与被选内容的关系 | 处理方式 | 解释边界 |
| --- | --- | --- |
| 只在同一提交里，或共享祖先 | 直接取 B、C 的选定状态 | 共同提交不等于内容依赖 |
| 是 B、C 演化的背景 | 用 Summarize 生成摘要 Artifact，并按需保留固定的外部引用 | 摘要有输入与覆盖范围，但不等于完整历史 |
| 原有 Artifact 实际使用了 A | 保留固定的外部引用（`<分支>@<提交>::<id>`），或生成新的派生产物，或不选入该 Artifact | 原产物的 `USED` 不改写 |
| 项目要求结论不依赖 A | 由 Agent 重新检查、抽取或形成记录 | 切断历史或生成摘要都证明不了独立性 |

在项目内写入时，引用一个既不在项目中、也不在 `origin` 外部引用清单中的 id，报错。系统能保证的是“项目图中没有 A，项目历史中也不带 A”；“留下的理解从未用过 A”是另一个需要依据的语义判断。

### 5.4 摘要承接历史

- **Summarize 读历史。** 输入可以是 `Log`、`Show`、`Diff`、`AsOf` 给出的固定历史：明确的提交范围、对象版本、属性与关系的变化，以及相关的材料、Artifact 和 `message`。摘要由 Agent 写出，中间件只校验引用和结构并持久化。
- **采纳由提交记录。** 摘要 Artifact 自身的输入谱系说明它从何而来；采纳它的提交说明它何时、以什么作用进入哪个项目。两者用固定引用关联，不合并为同一种父子关系。
- **精确恢复不能靠摘要。** 摘要只为项目保留可用的经验，不负责恢复旧值、执行 `Revert`，也不保证历史查询的答案不变。如果项目只保留摘要、不保留上游明细的访问能力，要显式记录这一边界。

前提是 `USED` / `inputs` 要能引用提交或历史范围。这会触及模型冻结与层次划分（提交对象属于机制层），尚待讨论。

## 6. 整合

### 6.1 单父历史：重放并核对改前值

整合不使用双父合并提交，也不做自动三方合并：

- **`Sync(project)`：** 把 main 上、项目来源基线之后的提交逐个重放到项目分支。
- **`Promote(project, commits)`：** 把项目分支上选定的提交逐个重放到 main。
- **重放时核对前提：** 对每一项修改，核对改前值是否等于目标的当前值。一致就应用；不一致就是冲突，此时暂停，由 Agent 交一份 graph-doc 作为决议，决议本身也是一个新提交。
- **可选做法：** 借鉴 TerminusDB rebase 的 `continue` 策略，把无法应用的提交标记为 invalid、记在链上，以便一次吸收大量变更。

这种核对只看前提值，不需要共同祖先，因此适用于以新根建立的项目。id 由全局计数器分配、与分支无关，所以同一对象在全局和项目中的 id 相同，重放时不需要做 id 映射。不过重放之后，每个提交的变更集都要按目标上实际生效的内容重新计算。

### 6.2 按子图回流：先求差异，再写入

如果回流的是一组对象而不是一组提交：先求项目分支上 `根 ↔ 头` 之间、限定在选定节点集合内的 `Diff`，把它当作一份 graph-doc，在 main 上走正常的 dry_run 和 apply。查重、端点校验、`confirm` 全部复用，生成的提交自带新算出的变更集。

### 6.3 回流前重新查重

全局和项目可能各自建了同一个对象（比如两边都入库了同一篇论文）。回流时要按 dry_run 的规则重新查重；判定结果和 `confirm` 记入回流提交。

### 6.4 冲突的三个层次

| 层次 | 例子 | 中间件 | 外部 Agent |
| --- | --- | --- | --- |
| 身份与写入 | 同一属性在两侧改成不同的值 | 核对改前值，检测后阻塞 | 给出明确的选择 |
| 结构与作用域 | 一侧删除了某个 Material，另一侧新增了依赖它的 Artifact | 校验引用、类型、端点、成员范围与原子性 | 补齐引用，或调整计划 |
| 语义分歧 | 两份 Observation 对同一方法给出不同结论 | 保存各自的来源、条件、判断者和显式关系 | 判断是否矛盾、是否可比、如何采纳 |

对象级没有冲突，不能说明图状态合法；图状态合法，也不能说明知识判断为真。

## 7. 存储与恢复

### 7.1 候选物理组织

逻辑历史先成立，物理组织可以替换。下表是候选空间，不要求同时实现。

| 组织方式 | 优点 | 代价 |
| --- | --- | --- |
| 每条分支一份完整图，所有分支共用提交链 | 最简单，读取直接 | 复制成本；Neo4j 社区版要开多个实例，或在同一个库里划命名空间 |
| 完整变更日志 + 逆向或正向重放 | 写入紧凑 | 历史越长，重放越慢 |
| 检查点 + 增量 | 控制重放长度 | 检查点的生成、调度和保留 |
| 不可变对象 + 成员/版本映射 | 多个项目共享内容 | 索引、成员维护、读取时过滤 |
| DeltaGraph 一类的历史索引 | 多个状态共享恢复路径 | 构建、参数与正确性验证都复杂 |

### 7.2 压实

`AsOf` 和重放的成本随距离增长，而回看旧报告所依据的状态恰恰需要访问旧状态。因此提供 `Squash` / `Checkpoint`：把一段历史压成带全量快照的检查点，此后的 `AsOf` 和重放都从最近的检查点出发。项目根提交本身就是一个检查点。

### 7.3 保留与回收

保留根包括项目基线、仍存在的分支，以及需要审计的历史状态。从保留根出发能到达的图记录、材料和 Artifact 文档都不能被回收。如果允许裁剪历史，要明确哪些状态因此失去完整读取能力。不能只保留哈希，同时又承诺可以复查旧报告的全部原始依据。

## 8. 正确性目标与不变式

| # | 不变式 |
| --- | --- |
| 1 | **重放一致：** 从根（或检查点）开始，按顺序重放一条分支上的提交，得到该分支的当前状态（派生字段重新计算） |
| 2 | **可逆：** 从任一提交写入后的状态逆向执行它的变更集，得到写入前的状态 |
| 3 | **原子：** 图的修改、提交对象与分支头在同一事务内发布；不存在没有提交记录的修改 |
| 4 | **文件完整：** 可见提交引用的每个文件都存在，且哈希一致 |
| 5 | **物理无关：** $\operatorname{ReadAt}$ 的结果与物理组织无关；压实前后 `AsOf`、`Diff`、`Blame` 的结果相同 |
| 6 | **分支隔离：** 一条分支上的写入不隐式改变另一条分支的状态 |
| 7 | **选择不是删除：** 整合不会把“未选入”变成目标上的删除 |
| 8 | **约束保持：** 从合法状态出发，被接受的变更（含整合）产生满足类型、身份、引用、作用域和内容可访问性约束的状态 |

这些约束都不能证明论文判断为真。查重、证据解释、摘要是否忠实、是否足以支撑项目任务，仍由外部 Agent 和独立的质量评价负责。

## 9. 评价边界

- **先评中间件。** 检查继承结果、作用域、输入版本、提交记录和历史读取是否正确；比较交互成本与维护成本的变化。
- **再评项目中的使用。** 摘要是否忠实、上下文是否充分、下游任务质量如何。快照恢复正确、来源链接存在，都不能说明摘要保留了所有重要条件。
- **成本要算全。** 包括项目构造、摘要生成、历史保存、材料保留和事后补查，不能只报告局部图变小带来的收益。
- **候选对比。** 以 A、B、C 为例，比较完整保留、固定外部引用、摘要承接和新根初始化几种方式。具体任务、预算、材料访问环境和质量标准另行讨论确定。

## 10. 当前工程的折扣版

当前工程先做线性历史，分支之后再做。对照如下：

| 完整机制 | 当前工程 |
| --- | --- |
| 统一写入底层、变更集、提交对象（§3） | **做。** Commit 工具与 Agent 算子都接入。提交对象取代 IngestBatch |
| `message`、`touched`、`removed`、`confirm`、`rounds` | **做** |
| 跨图与文件的原子性（§3.4） | **做。** 先写文件再提交事务；清理未被引用的文件 |
| `Log`、`Show`、`AsOf`、`Diff` | **做。** `AsOf` 用逆向重放 |
| `Blame`、`Revert` | 之后做。数据已经齐备，只差算子 |
| 不变式 1–4 | **做，写成测试** |
| 不变式 5–8 | 等分支与压实落地后再做 |
| Fork、根提交、`origin`（§5） | 之后做。物化方式倾向整图复制，先定 Neo4j 上怎么实现 |
| `Sync` / `Promote` 的重放与核对（§6） | 之后做，随分支一起 |
| 跨范围引用、外部固定引用（§5.3） | 之后做，随 Fork 一起 |
| Summarize 读历史、摘要承接（§5.4） | 暂不做，牵涉模型冻结 |
| 压实、检查点、保留与回收（§7.2–7.3） | 暂不做。规模小，项目根提交已起到检查点的作用 |
| 联合状态中的 $V_c$、$\Sigma_c$ | 简化处理：整图复制时，$V_c$ 就是该分支图里有什么；$\Sigma_c$ 只在提交上记一个版本号 |

## 11. 待定问题

1. 项目状态里具体包括什么（$V_c$ 是否需要单独存放）。
2. 初始化来源（`origin`）的具体格式，以及外部固定引用如何写入 graph-doc、如何解析。
3. Summarize 的历史输入怎样定位；`USED` 能否指向提交对象。
4. 只保留摘要时，要声明哪些信息边界。
5. 分支物化在 Neo4j 社区版上用多实例还是命名空间。
6. 重放时遇到无法应用的提交，是否允许标记为 invalid 后继续。
7. 项目内移除是否以及如何回流到全局。
